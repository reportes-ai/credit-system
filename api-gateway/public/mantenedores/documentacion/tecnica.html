Documentación Técnica

Arquitectura, tablas, motores e integraciones del Business Suite. Referencia para desarrollo y para el Administrador técnico.

Stack y arquitectura

BackendExpress.js + Node.js — microservicios independientes en /services/*/src/{controllers,routes}, montados por el api-gateway.
Base de datosTiDB Cloud (MySQL-compatible). Pool único compartido: shared/config/database.js. Timezone del pool alineado a Chile (gotcha mysql2: debe coincidir con SET time_zone o las horas se corren 4h).
FrontendHTML/CSS/JS vanilla en api-gateway/public/. PWA instalable (manifest + sw sin caché). App dedicada AF WhatsApp con manifest propio (scope /whatsapp/).
DeployGitHub main → Render auto-deploy (~2-3 min). APP_VERSION en public/js/app-version.js confirma el deploy en el badge de todas las páginas.
AuthJWT (shared/middleware/auth.js). Tokens separados: interno (usuarios), tipo=dealer (portal dealer), tipo=cliente (portal cliente). Permisos por requireFunc('codigo') contra la matriz en BD (Admin bypass, caché 60s). Regla "solo otorgas lo que tienes" (services/usuarios/src/otorgables.js): un no-Admin solo concede/quita funcionalidades que él mismo tiene, no toca el perfil Administrador y no asigna perfiles con permisos superiores a los suyos — enforcement server-side en matriz, masivo, overrides y crear/editar usuario. Auditoría de asignación (v200.8): TODO guardado que toca la matriz (perfil, overrides individuales y "Quiénes" de workflows) invalida el caché al tiro — el permiso recién dado opera de inmediato; y mis-permisos enciende la card del módulo también cuando el acceso viene de un override individual (antes solo miraba el perfil). Las casillas "_ver" de módulo y las de acción están cableadas a sus endpoints (auditoría §8 de scripts/audit-permisos.js); las que prometían acciones nunca construidas (clientes.eliminar, cotizaciones.aprobar/editar) se archivaron en el módulo Retirados, igual que el módulo Cartas de Aprobación Antiguo completo (app importada; /cartas-aprobacion redirige a /aprobaciones/ y sus 3 casillas vivas se movieron al módulo nuevo).
MigracionesIIFE (async () => {...})() al inicio de cada controller: CREATE TABLE IF NOT EXISTS + ALTER ADD COLUMN IF NOT EXISTS + seeds INSERT IGNORE. Pendiente: runner central (capataz) que las serialice.

Máximas de diseño (no negociables)

1. Un solo motor por cálculo: cada magnitud se calcula en UNA función compartida que usan todos los consumidores. 2. Una sola fuente de datos: cada dato vive en una tabla autoritativa; el resto la referencia por JOIN/FK. Snapshot deliberado (lo congelado al otorgar) ≠ duplicado. 3. Todo proceso nace documentado: cada feature se documenta al crearla (qué hace y para qué, cómo paso a paso con su pantalla, quién lo hace, prerequisitos, qué procesos afecta y cuáles dependen de él, y su flujo) en estos mismos documentos — un proceso sin documentar está incompleto. 4. Anti-hardcode: módulos y cards salen de las tablas modulos/funcionalidades, nunca de listas JS.

Fechas y horas: reglas que no se negocian

La base guarda en hora de Chile (el pool fija SET time_zone por conexión, -04:00 o -03:00 según horario de verano). NOW(), CURDATE() y DEFAULT CURRENT_TIMESTAMP entregan hora de Chile y son confiables. Todo lo que se rompió alguna vez vino de salirse de ahí.

1. Un timestamp de trazabilidad lo sella el SERVIDOR, nunca el navegador. Cuándo se creó, aprobó, rechazó, anuló u otorgó algo se escribe con NOW() y queda inmutable (COALESCE(col, ?) o un CASE que conserve el valor existente). 2. Distinto de una fecha de NEGOCIO —fecha de curse, de pago, de vencimiento— que el usuario elige a propósito y sí viaja en el formulario. 3. Para saber qué día es, shared/fecha-chile.js. Nunca new Date().toISOString().slice(0,10).

El episodio de las 4 horas (agosto 2026) — por qué existen estas reglas

El UPDATE que guarda una carta de aprobación escribía sus fechas con el valor que devolvía el navegador. El servidor las guardaba en hora de Chile, el navegador las recibía en UTC y las mandaba de vuelta tal cual: cada re-guardado corría la fecha 4 horas. Con dos ediciones, la carta saltaba al día siguiente.

Se descubrió porque el Centro de Control marcaba 2 cartas emitidas un domingo en que no se emitió ninguna. El diagnóstico completo: 504 de 532 cartas figuraban creadas después de su propia aprobación, 62 aprobadas después de estar otorgadas y 13 de 16 rechazos con la hora mala.

La fuente de verdad para repararlo fue auditoria_movimientos: registra cada acción con la hora del servidor y el cliente no puede tocarla. Regla que dejó: solo se corrige lo que se puede probar. Se exigió que el desfase fuera múltiplo exacto de 4 horas —la firma del bug— y se respetaron las cartas aprobadas o rechazadas más de una vez, donde quedarse con el primer registro habría pisado un dato bueno.
